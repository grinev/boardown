## Keep task edits merge-friendly across branches

---
id: BD-62
type: tech
status: done
order: 350
---

Editing a task on a feature branch currently produces the worst possible diff
for a three-way merge: a status change calls `placeTaskInContainer` with
`beforeTaskId: null`, so the task gets `order = max + step` and, because the
serializer writes tasks in array order, its whole block moves to the end of the
file. Two branches that each touched one task in the current release conflict
almost every time.

**The fix:** the physical order of task blocks in a file is stable — the order
they were parsed in — and a write never re-sorts them. `order` lives in
frontmatter only; sorting is the reader's job, which `ordering.ts` and
`BoardView` already do. With that in place, changing `order` costs one line
inside a task's own block, which merges cleanly, so the ordering rules
themselves can stay as they are.

Worth considering alongside it:

- An explicit normalize command, for whoever wants the file laid out in visual
  order again.
- Whether a status change should still send the card to the end of its column
  (today's behaviour, `order = max + step`) or leave `order` alone so the card
  keeps its relative position. A product call, not a merge one — both are safe
  once blocks stop moving.
- Context for whoever implements this: `order` is one number line per container,
  shared across all columns rather than per column, so the neighbours used to
  compute a midpoint may sit in other columns and gaps collapse sooner than
  expected. In the backlog the line spans every epic file at once, so a renumber
  there rewrites several files — fine, since the backlog is edited on the main
  branch only.

Out of scope: the ID collision problem (its own backlog task) and a semantic git
merge driver.
