A web board page whose theme is dark paints its first frame in the light palette, then switches once the theme is known. It happens on every page open and every browser reload. Inside a dark host window (an embed with `?embed`) it shows as a white flash. Live theme changes are not affected; they apply in place.

**Why it happens.** The served `index.html` carries no `data-theme`, so the stylesheet's `:root` light palette applies until the app has run. The theme is known only after a round trip:
- a shared theme (BD-144) after the page fetches `/api/shared-theme`;
- a board's own `theme: dark` after the board's `config.yaml` is read.

Both hosts behave the same way: the Vite dev shell and `boardown-web`, in single-board and registry mode alike.

**First step.** Confirm the flash is visible in practice and how long it lasts. It has not been measured.

**Direction.** The host puts the theme into the page it serves, so the first frame is already right: `data-theme`, and for a shared theme its token and font overrides. Today `boardown-web` serves `index.html` byte for byte and the dev middleware has no HTML transform, so both need one. Precedents:
- the VS Code extension stamps `data-theme` into the webview HTML it serves ([[repo:packages/vscode/src/extension.ts]]);
- Electron sets it before the app mounts ([[repo:packages/electron/src/renderer/main.tsx]]).

It must cover both sources of a theme, not only the shared one. Fixing one alone leaves the other flashing.

A URL fragment #task=<id> opens that task's dialog on the web board, so a host that embeds boardown-web (dev-studio, DS-87 there: a task id clicked in an agent terminal) can jump straight to a task. Works both on page load — the dialog opens once the board has loaded — and on a hashchange in an already open page, without reloading it: the board keeps its state and its SSE stream. Probed in Chromium (24.10.2026): a parent that sets a cross-origin iframe's src to the same URL with a new fragment gets a fragment navigation — same document, hashchange fires, also for a repeated identical fragment once the page has cleared it — while setting src back to the URL without a fragment reloads the frame. So after opening the task the page drops the fragment (history.replaceState), and the next click on the same id opens it again. An unknown id opens nothing and does not break the page. The store already has openTask(id); the work is in packages/web (read the fragment, listen for hashchange). Whether the dialog also opens a task in the backlog or a finished release, and whether the fragment is honoured outside ?embed, is settled in the spec.
