## CLI: apply a batch of operations from stdin

---
id: BD-107
type: feature
status: todo
epic: cli
order: 400
links:
  - type: relates
    to: BD-130
---

Setting up one board took 23 CLI calls: 4 epics, 10 tasks, 6 checklist items, 2 status marks, 1 link. Each round-trip can fail and leave the board half-built. `boardown apply -` reads a JSON array of operations from stdin and applies them through `writeAll` — all of them or none.

Needs grooming: how an operation references an id created earlier in the same batch, `--dry-run`, the shape of the response (one result per operation), and what happens when a core invariant refuses mid-batch. Widening the published command set is the human's call.

## Agent skill: allow editing docs pages directly

---
id: BD-140
type: docs
status: todo
epic: cli
order: 900
---

The skill template [[repo:packages/cli/skills/boardown/SKILL.md]] tells the agent never to edit board files by hand and lists a docs page among the things the CLI cannot do, so the agent stops instead of writing one. The CLI has no command for docs pages, so this blocks a legitimate request ("create a docs page with the findings").

Add an exception: docs pages are plain Markdown, the agent creates and edits `.boardown/docs/<page>.md` directly and links them with `[[<page>]]`. Everything else under `.boardown/` stays CLI-only.

Suggested wording (already applied by hand to a local install, which `boardown skill install` will overwrite):

> When the CLI has no command for what is asked (renaming or removing a label in the registry, deleting an epic or a release), tell the user it cannot be done through the CLI and stop there.
>
> The one exception is docs pages: the CLI has no command for them, so create and edit `.boardown/docs/<page>.md` directly as plain Markdown files. Link them from tasks and epics with `[[<page>]]`.

---

A web board page whose theme is dark paints its first frame in the light palette, then switches once the theme is known. It happens on every page open and every browser reload. Inside a dark host window (an embed with `?embed`) it shows as a white flash. Live theme changes are not affected; they apply in place.

**Why it happens.** The served `index.html` carries no `data-theme`, so the stylesheet's `:root` light palette applies until the app has run. The theme is known only after a round trip:
- a shared theme (BD-144) after the page fetches `/api/shared-theme`;
- a board's own `theme: dark` after the board's `config.yaml` is read.

Both hosts behave the same way: the Vite dev shell and `boardown-web`, in single-board and registry mode alike.

**First step.** Confirm the flash is visible in practice and how long it lasts. It has not been measured.

**Direction.** The host puts the theme into the page it serves, so the first frame is already right: `data-theme`, and for a shared theme its token and font overrides. Today `boardown-web` serves `index.html` byte for byte and the dev middleware has no HTML transform, so both need one. Precedents:
- the VS Code extension stamps `data-theme` into the webview HTML it serves ([[repo:packages/vscode/src/extension.ts]]);
- Electron sets it before the app mounts ([[repo:packages/electron/src/renderer/main.tsx]]).

It must cover both sources of a theme, not only the shared one. Fixing one alone leaves the other flashing.
