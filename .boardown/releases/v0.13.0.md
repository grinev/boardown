Opening a Markdown document makes ordinary body text visibly larger than task titles on the board.

Reproduction: compare a task card title on the Board tab with an ordinary paragraph in a document opened in Docs, a document popup, or a repository .md file preview.

Actual: board card titles explicitly use 14px (packages/ui/src/components/BoardView.module.css, .cardTitle), while MarkdownContent.module.css sets no base font-size. DocsView, DocPopupDialog and RepoFilePopupDialog do not set a body font-size either, and theme.css does not set one on body. Markdown paragraphs therefore inherit the host default (normally 16px in a browser, approximately 14% larger than 14px). All three document surfaces use MarkdownContent. Confirmed by source/CSS inspection on main; browser computed styles have not been measured.

Expected: ordinary Markdown body text uses a consistent base size aligned with the board text across Docs and both popup previews. Preserve the visual hierarchy of Markdown headings.

Move Docs loading off the board startup path. Load the tree or document lookup only when Docs, a doc link, or doc autocomplete needs it; load an individual page body only when that page is opened. Preserve existing navigation, titles, edit guards and refresh behaviour, with loading/error/retry states instead of false empty or missing results. Other task containers keep their current loading behaviour in v0.13.0; their deferral is tracked in BD-153.

Evidence from Dev Studio DS-133, boardown-web 0.12.0, 16 Nov 2026: three fresh Electron launches against an isolated copy of the Dev Studio board took 1413/1393/1380 ms from the board-tab click to a visible DS-133 card title, with 346 HTTP requests. The first iframe document request began after 190/169/171 ms. A diagnostic copy without the docs directory took 891/890/909 ms and 46 requests. The roughly 300 extra requests came from eagerly traversing and reading documentation, including old task plans. This experiment is not a proposal to delete Docs. The originally reported five-second delay was not reproduced; OS caches were not cleared and the installed Dev Studio build was not benchmarked.

Compare the packaged web embed before and after on the same unmodified board copy and report time, request count and payload bytes. No fixed performance threshold, Dev Studio changes or npm publication is part of this task.

## Detect and safely repair duplicate task IDs

---

Parallel branches can create different tasks with the same numeric ID. Today a lookup may silently select the first copy. Detect and report every duplicate, preserving the existing BD-123 format and nextId allocator. Never choose a task for an ambiguous lookup or targeted edit.

Provide explicit safe repair in the UI and CLI, and automatically include independent safe repairs in the first successful ordinary task mutation. Read-only operations only report duplicates. The copy with the uniquely earliest valid createdAt keeps the old ID; update only mirrors whose ownership is unambiguous, and notify the user after a successful repair. A missing or tied date, ambiguous links, board text references, attachments or write guard failures leave the affected group unchanged. BD-154 covers guided repair of ambiguous cases. Allocation across branches, the counter file and same-container Git merge conflicts are out of scope.
